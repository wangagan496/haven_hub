# 本地备份、维护与隔离恢复

日期：2026-10-29。适用版本：数据库 schema 13；本手册提供已验证的本地操作入口，不代表生产部署、异地备份、真实数据容量或恢复时限已经验收。

## 已提供的命令

在 `D:\haven_hub\server` 执行，源文件必须存在，目标父目录事先建立，目标目录本身必须不存在；替换下列示例目录，不要复用已有备份目录。

```powershell
npm run backup -- create data/haven.sqlite D:/haven-backups/release-20261028
npm run backup -- verify D:/haven-backups/release-20261028
npm run backup -- restore D:/haven-backups/release-20261028 D:/haven-restores/candidate-20261028
```

`create` 使用 SQLite 在线备份接口取得一致快照，覆盖已提交的 WAL 数据及数据库内的图片；服务运行时不要用文件复制代替。输出目录包含 `database.sqlite` 和 `manifest.json`。清单记录版本、时间、文件 SHA256、每张表的行数和内容摘要，校验同时执行完整性与外键检查；它检测损坏，不提供防恶意篡改的签名保证。

Windows 在写入数据前将新目录权限限制为执行账号与 SYSTEM，POSIX 目录权限为0700。执行账号与最终服务账号不同的部署，需要由负责人明确配置目标数据目录权限；不能因此给所有用户开放读取。明文命令不提供加密；加密命令和双份备份任务见下节，密钥托管与真实异地调度仍未验收。

2026-11-15权限修复：`createPrivateDirectory` 在Windows使用系统Windows PowerShell的.NET权限接口，按实际进程身份SID重建新目录访问规则，关闭继承，只允许执行账号与SYSTEM完全控制，并允许目录内后续新文件与子目录继承；随后回读核对全部规则、主体、权限及继承标记。原来的 `icacls /inheritance:r /grant:r` 没有清除其他显式授权，在父目录没有可继承权限时可留下Windows默认访问规则。现在不使用 `USERDOMAIN` 拼接账号，也不依赖权限显示名称或PowerShell安全模块自动加载；中文、空格和命令特殊字符路径以环境值按字面传递，不拼进脚本源码。

新目录权限设置或回读失败时不写入备份、凭证、监控和日志数据，只尝试删除本次创建的空目录；清理失败仍返回固定错误，可能留下空目录，不递归删除意外出现的其他内容。父目录须可信，系统Windows PowerShell须可用且获准执行；权限处理不成功就拒绝继续，不降级为开放权限。本次不修改既有目录权限，已有目录仍须由负责人按最终服务账号复核；不防同账号、管理员提权或磁盘直接访问，也不替代目标部署环境验收。

`restore` 只恢复到全新目录并再次核对清单，不替换活动数据库，也不自动切换服务。目标存在、备份损坏或权限设置失败时返回非零；已有目录不被覆盖。失败后的临时产物只清理本次创建目录内的已知文件，不递归删除外部路径。

## 加密备份与密钥

在同一个PowerShell进程中执行下列命令；目标父目录须先存在，示例路径应替换为本次新路径。`keygen`独占创建一个限制权限的新目录和32字节二进制密钥，不输出密钥内容；环境变量只传密钥文件位置，不能将密钥值放入命令参数。

```powershell
npm run backup -- keygen D:/haven-backup-keys/key-20261029
$env:BACKUP_KEY_FILE='D:/haven-backup-keys/key-20261029/backup.key'
npm run backup -- create-encrypted data/haven.sqlite D:/haven-backups/release-20261029
npm run backup -- verify-encrypted D:/haven-backups/release-20261029
npm run backup -- restore-encrypted D:/haven-backups/release-20261029 D:/haven-restores/candidate-20261029
Remove-Item Env:BACKUP_KEY_FILE
```

`create-encrypted`复用在线快照，再逐块加密数据库和清单，成功目标只有`database.enc`与`manifest.enc`。格式v1为8字节HAVENBK1头、12字节随机nonce、密文、16字节认证标签；固定AES-256-GCM，头和逻辑文件名同时参与认证。原始密钥是随机二进制文件，不接受口令、十六进制文本或Base64文本代替。

创建和校验会在对应备份根目录下创建`.haven-backup-private-进程号-UUID`私有明文暂存目录，不再使用系统临时目录；Windows只授予执行账号与SYSTEM访问，POSIX目录权限为0700。恢复将明文流写入新的私有候选目录，两个文件的认证标签通过后才打开SQLite并核对数据库完整性、外键、schema及全部表摘要。正常失败会删除本次创建的已知文件，正常校验结束会移除暂存目录，不能把这一清理当作磁盘安全擦除。强制终止或机器断电可能留下受限权限的暂存数据或不完整密文，须核对所属进程和路径后人工清理，重新执行verify-encrypted成功前不能把目录标为有效备份。

恢复成功的候选库是明文；CLI用destinationEncrypted=false标明，不能直接把它当作加密离机备份上传。创建和回读可能同时保留两份明文快照及密文，应预留磁盘空间；大规模数据的内存、耗时和磁盘峰值尚未验收。

密钥与加密备份应放在不同受控位置，并保存对应关系；本地生成器不强制跨设备分离，也不提供云密钥托管。轮换时用新密钥创建新备份并验证恢复，旧密钥保留到所对应备份按批准策略过期；丢失唯一密钥后本工具无法恢复备份。不要将密钥提交仓库、复制进备份目录或上传到同一存储位置。

## 维护窗口中的升级顺序

1. 在项目根目录运行 `pwsh -File tool/check_project.ps1`；本机已安装且已核对依赖时可用 `-SkipRestore`，干净环境不要跳过安装。保存构建版本、配置版本和检查日志。
2. 停止当前正常服务，确认其退出，并停止其他可能写库的演示实例、管理脚本或后台进程。仅关闭页面、拦截写接口或修改环境变量不构成停写；普通 GET 也可能触发到期结算。
3. 为独立维护进程配置 `MAINTENANCE_MODE=true` 并启动 `npm start`。它不打开数据库、不迁移、不运行结算或推送；`/health` 返回200且 `data.mode=maintenance`，`/ready` 以及所有业务读写返回503和 `Retry-After: 60`。维护进程健康不代表业务就绪，也不会停止其他已运行实例。
4. 对停止写入的源数据库执行 `create` 和 `verify`，保留这份不可变备份及对应旧程序和配置。不要把备份目录直接交给新程序运行，迁移会改变备份内容并使校验失效。
5. 执行 `restore` 到新候选目录。使用新版本程序、独立本地监听地址和候选 `DATABASE_PATH` 完成迁移及业务验收；候选环境不得使用真实外部推送凭据，合成账号和数据不得写进活动数据库。记录 schema、关键字段、行数、权限和联调结果。
6. 未恢复业务写入时，候选失败就保留原数据与旧程序，停止候选进程并调查；需要恢复时，再从未改变的备份恢复到另一个新目录，用匹配版本程序验收，加密备份还须提供对应密钥。旧程序不能直接连接不支持的 schema 13 数据库，禁止取消版本保护或手改 `user_version` 冒充旧库。
7. 验收通过后停止候选和维护进程，由操作负责人将正常服务指向已验收数据目录，设置 `MAINTENANCE_MODE=false`，启动并检查 `/ready` 与关键业务流程，再重新开放写入。明确记录开放时间；不得同时启动多个正常实例写同一个库。

本轮完成了独立维护入口和备份、校验、隔离恢复命令验收；尚未对实际部署系统执行从停写到重新开放的整套发布切换，因此第2—7步是操作规程，不是已完成的生产演练声明。

## 恢复写入后的故障

备份只包含其一致快照时刻的数据，随后成功提交的记录不在旧快照内；恢复旧快照可能丢失它们。先停止新写入并保留故障现场与新数据，核对备份后的报修、回执、房屋、访客及通知变化，再决定向前修复或经负责人确认的数据恢复。当前没有已验收的自动补录或重放工具，不能承诺“零数据损失回退”。

恢复目标、备份频率、保留期限、异地位置、负责人及允许的数据损失均待确定；目标文档中的4小时和1小时仍只是建议，不是已接受的保障。

## 双份备份、保留清理与调度入口（2026-10-29）

`server/src/backup-job.ts`提供一次执行的备份任务，复用原在线快照和加密格式，不给应用主进程增加后台定时器。先准备数据库、单独存放的密钥及两个备份位置；备份根目录的父目录必须存在，根目录首次使用时可不存在或为空，随后通过专用标识绑定原数据库的规范路径。两个根目录不能相同或互相包含，数据库和密钥不能位于任何备份根目录内；检测到别名后仍按真实路径核对。数据库迁移到新路径时使用新的备份根目录，保留原根目录供恢复。

复制`server/backup-job.example.json`并按实际位置修改，所有相对路径以配置文件目录为准；`keep`必须明确填写且至少为2，示例48只表示每处保留最近48个成功快照，不是已批准的生产保留期限，也不是48小时的数据保护承诺。备份频率与恢复目标仍需另行确定。开发入口：

```powershell
npm run backup:job -- D:/haven-operations/backup-job.json
```

调用前以`BACKUP_KEY_FILE`指定已有二进制密钥文件位置。编译后的入口是`node server/dist/tool/backup-job.js <配置文件>`。Windows调度入口先核对固定Node版本、读取配置和密钥文件位置，再运行构建产物并将脱敏结果保存为本次独立日志：

```powershell
pwsh -NoProfile -File D:/haven_hub/tool/run_backup_job.ps1 -ConfigFile D:/haven-operations/backup-job.json -KeyFile D:/haven-backup-keys/key-20261029/backup.key -LogDirectory D:/haven-operations/logs
```

运行前执行`npm run build`，不要让调度器依赖交互式终端的当前目录。Windows任务计划程序可使用上述PowerShell程序和参数，由已授权且能访问数据库、密钥及两个目标位置的账号运行；按批准频率设置重复触发、失败重试和“已有任务运行时不启动新实例”，并保留退出码和日志。要在退出登录后运行，须在系统中配置对应账号的后台运行权限，访问网络副本时还须验证该账号的网络权限。当前未注册系统定时任务，未录入账号凭据，也没有验收关机漏跑、断网恢复或后台账号访问。

每次任务按顺序执行：

1. 在两个根目录独占创建锁，记录进程号与启动时间。只有操作系统确认原进程不存在才接管并记录`backup_lock_recovered`；仍存活、权限不足或无法识别的锁返回明确的“锁被占用”。不按文件年龄判断进程死亡。加锁失败会释放本次已取得的另一个锁；释放其中一把失败仍会尝试释放另一把，不删除他人的锁。
2. 在本地`.pending-UUID`目录创建并回读校验加密快照，再只复制`database.enc`和`manifest.enc`到副本的私有暂存目录，解密验证副本的认证标签、数据库完整性及清单摘要。
3. 两份均通过后分别重命名为`snapshot-时间-UUID`；回执包含快照名称、schema、完成时间、份数、删除数量、`status`及`invalidSnapshots`，没有数据库内容、表清单或密钥。
4. 默认只对本次新快照及其副本进行完整解密校验。旧快照仅核对目录、文件类型与最小长度，以及有大小限制的认证加密清单；不解密旧数据库。保留本次新快照及最近的合格旧快照，超额部分按清单时间清理，主机时钟倒退也不会删除本次快照。`keep`只统计合格快照，不包括已标记的异常快照；首次执行不虚构历史副本。

需要完整检查历史快照时执行`npm run backup:job -- D:/haven-operations/backup-job.json --verify-all`，或编译后的`node server/dist/tool/backup-job.js <配置文件> --verify-all`；这仍会先创建并验证一份新备份，再扫描旧快照。单独验证一个目录可使用`verify-encrypted`。默认检查无法发现所有数据库密文位翻转，完整校验应另行安排频率。

未知名称、`.pending-*`及其他根目录内容不参与自动删除。目录链接、额外文件、损坏数据及旧密钥快照会被保留并计入异常，其他过期合格快照仍照常清理；异常名称保存在各根目录的`.haven-backup-invalid.json`，后续普通任务不会误删已发现的损坏快照。修复后使用`--verify-all`重新检查，成功才解除标记。只删除合格快照中的两个已知文件，再删除空目录，不递归删除目录。备份或复制失败时不开始清理；若实际删除期间发生IO失败，可能已删除部分超额快照，不能保证清理全有或全无。

退出码0表示两份新备份成功且未发现历史异常；退出码2和`status=warning`、`database_backup_job_completed_with_warnings`表示两份新备份成功，但有旧快照异常，`invalidSnapshots`按本地/副本的异常目录数合计。退出码1表示执行失败（例如配置、复制或IO失败），不能假定本次没有产物。调度器应单独处理退出码2，保留异常快照并检查日志，不要把它记录成“新备份失败”或自动删除损坏目录。

副本复制失败会保留已验证的本地暂存快照，供人工校验与恢复，副本只清理本次创建的已知暂存文件；进程被强杀可能留下锁、暂存目录或只完成一处重命名的快照。锁按进程存活检查恢复，暂存内容仍须检查所属进程、目录和校验状态后人工处理。反复失败可能增加磁盘占用，不能用通配符删除所有暂存目录代替排查。轮换密钥时启用新的两个根目录，旧目录与旧密钥按批准策略保留；当前任务不会猜测旧密钥并删除对应快照。

两个不同目录只代表两份副本，不能证明跨磁盘或异地；配置为网络目录或挂载盘时，必须在调度前验证远端确实挂载、可写且属于预期存储，避免挂载失效后写入本机同名空目录。网络中断、断电持久性、远端账号权限和真实规模耗时仍须在目标环境验收。任务日志也需要单独的保存和清理策略。
