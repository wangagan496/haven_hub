# 本地运行指标与故障检查

日期：2026-10-29。对应 G4 的本地工程部分，覆盖服务指标、推送队列、按需检查、独立持续采集、故障/新鲜度检查、Windows运行入口和待导入任务定义，以及可选的脱敏运行日志持久化；没有接入外部告警平台，也没有安装系统定时任务或开机服务。

## 查看运行状态

GET `/management/operations` 沿用当前登录校验、账号停用检查、物业管理员权限和客户端最低版本门禁，返回标准业务响应中的 `data`。住户、师傅和未登录请求不能读取；响应禁止缓存。数据库查询每个来源 IP 每分钟最多12次，建议本地采集间隔至少30秒；当前服务不信任代理头，同一反向代理后的请求可能共享额度。

第二十四批增加独立机器入口 GET `/operations/snapshot`，默认关闭，只有显式设置 `OPERATIONS_KEYS_FILE` 后才启用；它使用下文的只读监控凭证和 `X-Operations-Version: 1`，不依赖用户登录或App最低版本，返回与管理员入口相同的汇总。该凭证不能访问住户/师傅/物业业务、图片或刷新接口；两种凭证不能混用。机器入口有独立的每来源IP每分钟12次额度，错误凭证、错误协议和非GET请求也占额度，避免反复读取密钥配置。两个指标入口均不进入业务指标分母。

返回字段分为以下两组。

| 字段 | 含义 |
| --- | --- |
| `requests.completed` / `serverErrors` / `serverErrorRate` | 已结束的业务请求数、HTTP 5xx数及占比；未完成连接不进入错误率分母 |
| `requests.rejected` / `authRejected` | HTTP 4xx或已有错误处理器返回的业务拒绝；验证码错误即使HTTP 200也会计数，认证组包括取验证码、登录及刷新 |
| `requests.rateLimited` / `aborted` / `activeRequests` | HTTP 429、响应未正常结束就断开的请求、当前未结束请求；断开不证明服务端业务未提交 |
| `requests.latency` | 已结束请求的固定耗时分桶和P95桶上界；不是精确分位数，也不是完整客户端体验耗时 |
| `requests.notificationSyncFailures` / `notificationStartupFailures` | 待办同步及启动重建异常次数 |
| `requests.pushDispatchFailures` / `pushTransportFailures` / `smsSendFailures` | 已有对应日志事件的次数；是事件计数，可能与请求错误重叠，不能相加当作独立故障总数 |
| `push.queued` / `failed` / `sending` / `accepted` | 当前有效待办的投递状态数；`accepted`仅表示外部服务接受，不表示手机已收到 |
| `push.due` / `oldestDueDelayMs` | 已到执行时间、未耗尽重试且设备归属匹配的投递数及最早到期任务拖延多久；退避中的任务不是到期积压，拖延也不是通知总年龄 |
| `push.stopped` / `expiredLeases` | 重试耗尽的排队/失败记录数、超时但尚未恢复的发送领取数 |
| `push.unconfigured` / `expired` | 未配置推送服务、已失效订阅的有效待办投递数 |
| `push.orphaned` / `unknownStatus` | 排队/失败/发送状态却缺少所属设备的记录、未知投递状态；检查命令将其作为状态异常 |

请求指标用单调时钟聚合，最多60个10秒桶，保留当前桶及前59桶。窗口是约590—600秒的桶范围；不足一个窗口时用 `observedMs` 表示实际覆盖时长，进程重启归零。每个请求按结束时刻归桶，超过窗口的在途请求仍由 `activeRequests` 表示。固定字段不按账号、IP、路径、任意客户端版本或异常内容创建标签，不保留请求体、凭证、自由文本和用户标识。

耗时桶上界依次为50、100、250、500、1000、2000、5000、10000毫秒和无穷大，各桶是非累加计数；例如上界250表示落在前一个边界100到250之间。P95上界为空时，可能是没有样本，也可能P95超过10000毫秒，结合 `completed` 和最后一桶判断；检查命令在样本足够时把后者作为延迟告警。阈值最好选择现有桶边界，选择中间值会保守报警。

健康、就绪、指标自身以及 `/admin`、`/workflow` 静态页面请求不进入业务请求指标，防止轮询把错误率稀释；这些探测失败由检查命令独立报告。服务端现有排查编号和脱敏日志保留。推送统计只做聚合读取，不触发到期结算、发送、恢复或重试，不返回通知标题、内容、工单或设备编号；关闭的历史待办不计入。当前查询仍需扫描投递及关联表，限流不等于完成真实数据量性能验收。

## 运行一次本地检查

在仓库外准备运行配置和受限凭证文件；参考 `server/operations-check.example.json`，将其中路径改为你自己的目录。配置中的阈值必须逐项填写，示例仅用于本地演练，不代表已确认的试点标准。示例已选择 `authentication: "operations-key"`，凭证按下节生成；原有配置不填此字段时仍按 `admin-session` 运行，不会自动尝试另一种身份。

管理员模式仅用于兼容已有人工检查：凭证文件为 `{"token":"<当前物业管理员的64位十六进制access token>"}`，约30分钟到期，需通过既有登录流程更新，`clientVersion` 必须是真实受支持的版本。机器模式使用生成的 `ops_v1_` 前缀凭证，到期时间由操作者显式指定，不继承管理员会话权限或有效期；配置中的 `clientVersion` 字段为旧格式兼容而保留，机器请求只发送独立协议版本。

不要放刷新凭证、手机号或验证码。凭证文件只允许执行检查的账号读取，不写入仓库、命令行、公开日志或聊天；工具不自动登录、刷新或延长任何凭证有效期。

在 `server` 目录执行：

```powershell
npm run operations:check -- C:/private/haven-operations-check.json
```

命令按顺序请求 `/health`、`/ready`，再根据身份模式请求机器或管理员指标接口，只在最后一步发送对应凭证。只接受数字回环地址 `127.0.0.1` 或 `[::1]`，不使用DNS解析、不接受带路径/凭证/查询参数的地址，也不跟随重定向；每一步的超时覆盖连接和响应体，每个响应最多32KiB。它不会调用短信、业务写入接口或外部通知服务。

| 退出码 | `status` | 处理含义 |
| --- | --- | --- |
| 0 | `ok` | 当前采样数量足够，所有已配置阈值均未超限；不是生产交付通过 |
| 1 | `unavailable` | 配置/凭证无效、权限拒绝、版本不支持、限流、连接失败、超时、协议格式错误或就绪检查失败；不能当健康 |
| 2 | `alert` | 至少一项超限或推送状态异常；`reasons`给固定原因编号 |
| 3 | `maintenance` / `insufficient-data` | 维护模式或业务样本不足；不能当正常业务可用 |

阈值都采用“超过”才报警：例如 `maxStopped: 0` 表示出现一条耗尽重试记录就报警。错误率和P95需要达到 `minimumRequests`；样本不足期间仍检查认证拒绝、断开、后台错误和推送异常，返回样本数及5xx数供人工查看。统计的低流量单次5xx不会自动触发错误率报警，负责人可据本地需求调低最小样本数。

`reasons`包括 `server_error_rate`、`request_latency`、`auth_rejected`、`requests_aborted`、`background_failures`，以及 `push_due`、`push_overdue`、`push_stopped`、`push_expired_leases`、`push_unconfigured`、`push_invalid_state`。固定 `probe_failed` 表示探测未完成；用命令退出码、既有排查编号及服务端脱敏日志继续定位，报告不会回显原始响应、异常、凭证或文件路径。

## 生成、轮换和撤销只读凭证

先准备仓库外的父目录；目标目录必须全新。在 `server` 目录执行以下形式的命令，到期时间必须自己选择，示例日期不是生产保留政策：

```powershell
npm run operations:key -- C:/private/haven-operations-key 2026-11-28T00:00:00Z
```

生成器使用32字节系统随机数，并创建 `token.json` 与 `keys.json`；终端只输出凭证编号、生效时间和到期时间，不输出原文或摘要，也不覆盖已有目录。沿用项目已有权限封装：Windows目录仅执行账号和SYSTEM可访问，POSIX目录0700、文件0600。当前本机已实测Windows ACL；POSIX代码分支未在本轮实机验收。服务端与检查进程使用不同系统账号时，需分别安排摘要文件和原文文件的最小读取权限，并另行验收，不要开放整个目录给所有用户。

`token.json` 含原文，只给检查进程；`keys.json` 只含版本、编号、SHA256摘要和UTC生效/到期时间，不含原文。服务启动环境设置 `OPERATIONS_KEYS_FILE=C:/private/haven-operations-key/keys.json`，检查配置设置 `authentication: "operations-key"` 和 `tokenFile` 指向 `token.json`。默认空路径保持关闭；非绝对路径、文件不可读或结构错误会在打开数据库前阻止启动。

生效区间为 `notBefore <= 当前时间 < expiresAt`，所以到期的那一刻就失效；机器时钟仍须正确。每个请求重新读取最多4KiB的摘要文件并校验完整结构，用固定长度摘要比较校验原文，不缓存上一次可用的凭证。文件损坏、读取失败或被删除时返回503，不继续接受旧凭证；空列表 `{"version":1,"keys":[]}` 是有效撤销配置，所有旧凭证返回401。

轮换步骤：

1. 在另一个全新受限目录生成下一把凭证，先确认新旧有效期有重叠。
2. 将新摘要条目加入服务端的 `keys.json`，保留旧条目，最多允许2条且编号及摘要都必须唯一；通过同目录暂存文件替换正式文件发布完整JSON，避免把半写文件暴露给读者。短暂损坏会使探测报告不可用，不会保持旧授权。
3. 切换检查配置的 `tokenFile` 到新凭证，运行检查，确认协议/权限没有失败；样本不足仍可能返回3，不能仅用非零退出码判断新凭证无效。
4. 删除服务端旧摘要条目；下一次请求开始旧凭证即被拒绝，不需要重启。全部撤销时发布空列表；撤销已通过权限校验的在途读取无法追回，撤销不涉及其他用户会话。

正常读取不依赖短信、管理员账号或其续期。服务本身仍只监听回环地址，但反向代理可能把同一端口转发到外网，因此生产代理应禁止向公网转发 `/operations/`；本机数字回环检查不是代理隔离验收。实际密钥托管、轮换负责人和到期提醒需结合部署落地，本轮只在隔离测试目录生成并清理演练凭证，未配置日常服务或建立定时采集任务。

## 持续采集与本地故障记录

第二十五批新增独立进程 `operations:monitor`，复用只读检查；与业务服务分开运行，业务服务退出后仍可记录探测不可用。它是前台常驻命令，终端关闭后不承诺继续工作，不会自行注册Windows任务计划、系统服务或开机启动。

在仓库外保存配置，参考 `server/operations-monitor.example.json`，所有参数必须显式填写：

| 配置 | 含义 |
| --- | --- |
| `checkConfigFile` | 前文一次性检查的配置文件，持续采集只允许 `authentication: "operations-key"` |
| `directory` | 全新专用日志目录，父目录须存在；重新启动可以使用同一采集器之前创建的目录 |
| `intervalSeconds` | 一次检查完整结束后等待多久才开始下一次，30—3600秒；单次最多串行执行3个有超时的HTTP请求，因此不是固定起点频率 |
| `failureSamples` | 连续多少次 `alert` 或 `unavailable` 后建立故障，1—10；两类失败交替也算连续失败 |
| `recoverySamples` | 已有故障后，连续多少次 `ok` 才记录恢复，1—10 |
| `retentionEvents` | 保留最近多少条事件，100—100000，含采样、状态变化和进程启停；示例10000不是生产保留政策 |

配置中的相对路径以配置文件所在目录为基准；启动时读取采集参数、检查目标和阈值，运行中不热改这些配置。每次探测都会重新读取同一路径的凭证原文，因此替换 `token.json` 后无需重启即可使用新钥匙；改变 `tokenFile` 路径需要重启。目标来源、阈值、HTTP超时、采集间隔或确认次数变化时要求使用新日志目录，不把不同判定条件下的故障状态混在一起；仅改凭证路径或保留条数可复用原目录。

在 `server` 目录运行：

```powershell
npm run operations:monitor -- C:/private/haven-operations-monitor.json
# 有限次数演练；不改变最小30秒间隔。
npm run operations:monitor -- C:/private/haven-operations-monitor.json --cycles 3
```

命令持续输出固定结构JSON事件，同时写入专用目录下的 `monitor.sqlite`。输出只有序号、UTC时间、采集进程编号、事件类型、固定状态/原因和故障编号，不保存请求内容、原始异常、凭证、账号、设备、服务地址或文件路径；它也不保存完整历史指标快照，定位具体请求仍用原有排查编号和服务日志。

| 事件 | 含义 |
| --- | --- |
| `collector_started` / `collector_stopped` | 采集器启动/正常结束，不能解读为业务恢复 |
| `sample` | 一次已完成探测的状态；每次都保留，便于发现采集中断和未知状态 |
| `incident_opened` | 达到连续失败次数后建立一个故障编号 |
| `incident_updated` | 故障仍在，但失败种类或原因集合变化；同样的持续失败不会重复建故障 |
| `incident_recovered` | 达到连续健康次数，关闭同一故障编号 |

`maintenance` 和 `insufficient-data` 都是未确认健康，清零连续计数但不关闭已有故障；维护结束后仍需足够的 `ok` 才恢复。没有故障时偶发一次失败不会在随后好转时伪造“恢复”记录。故障已建立后，新的失败原因立即更新，不另等一次确认；低流量业务长期样本不足也会阻止自动恢复，需要根据实际规模确定一次性检查的最小样本数。

采样、故障变化和事件保留清理在单个SQLite事务内提交；提交失败会停止采集并非零退出，不打印虚假的成功采样或恢复。输出发生在提交之后，数据库是持久化依据，进程在提交后突然退出可能来不及向终端输出最后几条；这不是外部消息恰好一次送达保证。

重新启动会读取尚未恢复的故障，保留其编号避免重复创建；连续确认计数重新从0开始，不假定停机期间持续好或持续坏。旧事件按序号清理而不依赖系统时间，当前故障独立保存，即使“打开故障”那条历史已超出保留上限也仍可恢复。保留条数限制逻辑记录数，不是磁盘字节硬配额；SQLite/WAL空间与外部长时间读事务仍需部署层容量管理，未提供生产日志留存承诺。

正常结束或Ctrl+C/SIGTERM会取消当前HTTP探测及等待，主动取消的请求不计故障，随后记录停止并关闭数据库、释放进程锁；有限次数运行正常结束同样返回0，这个退出码仅表示采集器正常完成，不表示被监控业务健康，业务状态应读事件或使用 `operations:check`。采集器自身的配置、写盘或锁异常返回1并输出固定 `collector_failed`，不会回显原始异常。

目录由原有私有目录封装创建，Windows限制执行账号/SYSTEM，POSIX使用0700/0600；已有目录拒绝符号链接及未知文件。`collector.lock` 防止两个进程同时写同一目录；硬杀或断电后可能遗留锁，本轮不自动抢占。恢复时先确认旧采集进程已退出，再核对锁文件中的PID/运行编号并人工删除该目录中的这一锁文件，不删除数据库或WAL；仅凭PID未出现不能证明另一个复用PID的进程是原采集器。损坏数据或不同目标配置会拒绝启动，不自动清库。

可在支持SQLite的工具中以只读模式打开 `monitor.sqlite`，通过 `SELECT seq,at,event,status,reasons,incidentId FROM events ORDER BY seq DESC LIMIT 100` 查看最近记录，或读取 `state.incident` 判断是否有未恢复故障；运行中的数据库不要直接复制，需停采集或使用SQLite在线备份方式。故障记录可由拥有目录写权限的人修改，不是不可篡改的审计凭证。

## 独立检查采集器是否仍在采样

第二十六批增加以下一次性命令，读取同一份持续采集配置，在采集器退出后也能单独运行：

```powershell
cd server
npm run operations:monitor:status -- C:/private/haven-operations-monitor.json
# 已构建的部署产物也可直接运行，stdout只有一行JSON。
node dist/tool/operations-monitor-status.js C:/private/haven-operations-monitor.json
```

检查进程不发送HTTP、不读取凭证原文、不打开SQLite、不查杀进程，不创建目录、获取或清除采集锁，也不注册系统任务；它只读取配置、目录信息、锁和最多4KiB的状态文件。实测Node的只读SQLite连接仍可能创建WAL/SHM辅助文件，因此本入口改用采集器在数据库事务提交后发布的 `collector-status.json`，避免检查动作改变日志目录；这不是数据库完整性检查，也不替代原有故障历史。

采集器将完整状态写入同目录独占临时文件 `collector-status.pending`，刷新文件后通过重命名替换正式文件；读者只能取得上一次或这一次完整发布的状态。数据库提交失败不会刷新状态，状态发布失败也会停止采集并非零退出，最后一份完整状态仍可用于判断超时。数据库提交和状态文件替换不是跨文件事务，突然退出可能使状态文件落后于数据库，因此检查保守报告未知或过期，不能反向声称数据库缺失了最后一条。断电后的目录元数据持久性未验收。

| 输出状态 | 退出码 | 含义与处理 |
| --- | --- | --- |
| `fresh` | 0 | 同一运行编号和PID的锁存在，最近已提交采样仍在期限内；不等于业务健康，也不证明该PID此刻仍在运行 |
| `starting` | 3 | 新进程已发布启动状态，尚未完成第一轮；在启动宽限期内仍不能报健康 |
| `stopped` | 2 | 已发布正常停止状态，包括有限次数运行结束；旧的健康样本不会覆盖停止状态 |
| `stale` | 2 | 第一轮或后续采样已经超时，即使旧锁和同名PID仍存在也不会判为新鲜 |
| `unavailable` | 1、2或3 | 配置、目录、状态或身份校验失败为1；非正常停止且锁缺失为2；检查前后锁变化为3，表示本次快照不稳定 |

`lastSample.status/reasons` 单独描述业务采样，允许外层 `fresh` 而内层 `unavailable`、`alert`、`maintenance` 或 `insufficient-data`；业务故障仍沿用 `operations:check` 和原故障事件判断。输出不含路径、URL、凭证、PID、运行编号或原始异常；`ageMs` 是最新样本（尚无样本则启动时间）距检查时间的毫秒数。

启动宽限为 `3 × timeoutMs + 10000` 毫秒，已有样本的期限为 `intervalSeconds × 1000 + 3 × timeoutMs + 10000`；三个HTTP请求顺序执行，所以必须留足三次超时。10秒是本地调度和状态发布的工程余量，不是生产故障发现SLA；超过期限才报过期，恰好等于期限仍在范围内。检测最坏延迟还包含外部调用本命令的间隔。

这是一种有期限的采样证明：强杀发生在刚完成采样之后，短时间内仍可能为 `fresh`，到期后才可确定没有新进展。停采不能靠“锁文件存在”或“PID存在”证明仍在运行；本命令不自动抢锁或重启进程。未来时间、状态时间顺序矛盾，或同一轮运行中已观测到的系统时间倒退，都返回 `clock_invalid`；采集器会保留倒退标记，校正时钟并重新启动后才重新建立证据，重启也不会继承上一运行的健康样本。

第二十六批将HTTP超时加入目标指纹，防止运行中放宽检查配置而掩盖旧采集器停滞；第二十五批及更早目录没有该指纹和状态文件，必须停旧采集器、保留旧历史，并为新版配置一个全新日志目录，不能手改旧指纹或自动清库。状态检查遇到旧目录返回不可用，不替旧采集器伪造心跳。新版本同配置重启沿用新目录；持有新锁后只清除该目录中保留的固定临时状态文件，再发布新启动状态，原数据库和事件不清除。

独立命令仍需由人或部署层实际调用；本轮没有安装看门狗、开机托管、系统调度或外部通知，检查命令和采集器一同不运行时不会自动发现故障。状态文件和锁继承专用目录权限，同一有写权限账号仍可篡改它们，不是防篡改证明；不能据此将G4标记为生产完成。

## 服务启动、退出与异常收尾

第二十九批通过 `server/src/server-lifecycle.ts` 管理正式 `main.ts` 入口的退出。Node收到已注册的SIGINT/SIGTERM处理事件后，先停止接受新连接并关闭空闲连接，同时停止新的周期结算/推送调度；等待已有HTTP响应与已经开始的推送任务结束，然后关闭资源。重复关闭事件共用同一次收尾，不重复关闭数据库，也不会延长等待期限。

默认等待上限沿用5秒。期限到达仍未结束时，记录 `server_shutdown_timeout`，销毁剩余HTTP连接，尽力刷新关闭日志并以1退出；不会在仍有任务使用数据库时调用同步关库。期限定时器保持进程存活，避免只剩一个未完成Promise时提前自然退出。同步SQLite、文件系统或CPU操作仍可能阻塞事件循环，所以5秒是可调度时的等待期限，不是硬实时终止保证。

正式入口的退出码0仅表示本次正常收尾没有已知失败；配置、初始化、监听、后台停止、资源关闭、日志写入/刷新、超时或进程致命异常均返回1。`uncaughtException` 和 `unhandledRejection` 只记录固定事件、停止接收新连接并进入有期限的退出，绝不会记录后继续长期服务；普通由Express处理的业务失败仍按原HTTP协议返回，不因一次普通500响应自动终止整个服务。

| 事件 | 含义与记录位置 |
| --- | --- |
| `server_config_failed` | 环境文件读取或配置校验失败；日志尚未初始化，仅标准错误输出 |
| `server_start_failed` | 应用/数据库初始化失败；标准错误输出，已经成功打开的运行日志也会记录 |
| `server_listen_failed` | 监听失败；标准错误输出，已打开的日志可同时记录 |
| `server_started` | HTTP已经开始监听；不替代 `/ready` 或业务健康检查 |
| `server_stopping` | 首次进入关闭流程，重复关闭事件不重复记录 |
| `process_uncaught_exception` / `process_unhandled_rejection` | 第一次进程级JavaScript异常，固定类别，不含异常消息、堆栈或配置原文 |
| `server_drained` | HTTP与后台等待已结束；不保证之后关库/日志刷新一定成功 |
| `server_shutdown_timeout` | 等待到期，使用失败退出，不视为正常完成 |
| `server_stopped` / `server_shutdown_failed` | 资源收尾后的最终结果，只写标准错误；此时应用运行日志已经关闭 |

上述进程诊断使用同步、固定字段的标准错误输出，输出失败不会再次抛出原始异常；正常业务服务启用文件日志时，在日志仍可写的阶段同步保存事件。`runtime_log_stopped` 仅表示日志模块收尾，不能单凭这条记录推断整个服务退出成功；最终结果须结合进程退出码及标准错误。配置失败按模板核对字段和文件权限，不通过恢复输出原始错误来排查，以免配置值进入终端日志。

推送停止继续沿用原有领取机制：当前外部发送返回后，停止中的调度器不会继续领取下一条，也不会把未确认的旧领取强行改为成功；原 `sending` 记录保留期限，重启后按现有规则恢复。关闭等待不等于外部消息撤回、确认设备收信或保证恰好一次送达。维护入口使用相同退出管理，但仍不创建业务数据库、推送任务或运行日志目录。

本机子进程测试通过内部触发同一已注册SIGINT/SIGTERM处理器验证正式入口；没有把它称为Windows系统实际投递信号、控制台关闭或任务计划程序停止验收。系统强杀、进程原生崩溃、内存耗尽、断电以及入口模块加载前的失败可能无法运行JavaScript收尾；日志/监控旧锁仍按原手册人工核实。没有加入自动重启、系统服务安装或完整发布切换。
