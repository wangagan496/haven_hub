## 启动

报修系统通知同时接入 HarmonyOS Push Kit 与 Edge Web Push。待办和失败重试保存在 SQLite，具体配置、权限、真机验收和状态含义见 [系统推送接入说明](../docs/system_push_setup.md)。未配置华为凭据时仍可使用工单与站内待办。

推送领取与恢复：每条投递在短写事务中复核当前待办、设备归属及内容、重试时刻和次数，然后写入唯一 `lease`；网络发送在事务外执行。复用 `nextAt` 保存状态对应的时间：`sending` 时是60秒领取期限，`failed/queued` 时是下次尝试时刻；实际外部请求超时保持10秒。启动及每次调度仅恢复已超时的 `sending`，不重置仍有效的领取；恢复保持尝试次数，达到5次则停为可手动重试的失败状态。结果落库与失效设备清理在同一事务再次校验领取标识、当前归属与订阅内容，旧响应不能完成替代任务或删除新订阅。

该保护已用隔离SQLite和两个独立Node进程验证领取竞争，但不承诺外部推送恰好送达一次：服务商已接收而本地落库前崩溃、长暂停超过领取期限，或用户主动再次提醒，仍可能重复通知；`accepted`仍仅表示服务接受。旧进程会重置全部发送中任务，升级前须停止旧进程，不能混跑；本批复用现有字段且数据库版本仍为11。完整多实例部署、长期负载、真机送达、远程告警和正式客户端支持期仍待验收。

在项目根目录 `D:\haven_hub`：

```powershell
cd server
npm ci
npm run build
npm start
```

默认监听 `http://127.0.0.1:3000`，首次启动自动建表，数据库在 `server/data/haven.sqlite`。停止服务用 Ctrl+C；再次启动数据仍在。Node.js 要求 24 或更高版本，内置 SQLite 可能显示实验性提示。开发时可用 `npm run dev` 自动重启。

本地自定义时，将 `.env.example` 复制为 `.env` 后编辑，无需短信密钥。生产必须显式配置 `NODE_ENV=production`、`AUTH_MODE=tencent`、HTTPS来源、独立数据库绝对路径、物业电话、客户端最低版本及完整短信参数；开发码、缺失凭据和不完整配置拒绝启动。`HOST` 继续只接受回环地址 `127.0.0.1`、`localhost`、`::1`，对外HTTPS由同机反向代理提供；代理与真实云端尚待部署验收，不能仅因配置通过就公开上线。

## 连接 App：保留真实腾讯地图

### 住户报修分页的内存控制

`GET /repair` 继续先完成该住户全部工单的到期结算，再按既有 `repairs_owner(userId, seq DESC)` 索引逐条读取并构造视图，只保留当前页。`rows/total/pageTotal/current`、默认20条和最多200条、顺序、电话脱敏及可操作字段不变；损坏记录仍跳过且不占分页位置，总数只统计成功生成的视图，查询游标出错则整体失败，不返回看似完整的部分结果。创建和撤销的完整列表响应继续沿用原契约。

这是列表组装阶段的内存优化，没有直接改成 SQL LIMIT/OFFSET：若在视图校验前分页，会使损坏记录占位、总数虚高；若只结算当前页，会遗漏页外到期状态和通知。当前仍遍历全部住户记录以取得准确总数，全局人手计算、到期结算和启动扫描的成本仍保留，没有新增索引或数据迁移。

第十六批新增可选查询 `filter=all|pending|waiting|processing|completed`，省略时默认为all；处理中包含状态2和6。先结算全部住户工单，再在成功视图上筛选、计算总数及页码，非all响应增加相同的filter回显，无效或重复筛选参数返回400。客户端核对筛选回显和返回状态，旧服务端忽略筛选参数时会报错，升级顺序应为后端在前。

Flutter首页预加载与我的报修默认只取第一页20条，点击“加载更多”才取下一页；筛选、刷新、详情返回和新增成功会重读第一页，迟到请求不覆盖新页面，换号清空旧数据，追加失败保留列表并允许重试。总数变化或重复编号会拒绝追加并提示刷新；仍使用页码读取各次当前状态，相同总数下并发替换记录不保证跨页快照一致性。原完整列表API及创建/直接取消完整响应继续保留，不表示所有请求都已改成有限条数；请求数量、筛选和竞态回归见生产化目标第十六批。

可在 server 目录执行 `node --expose-gc --import tsx tool/repair-pagination-benchmark.ts` 重跑独立内存数据库实验：6000条合成工单、每条20个事件、每页20条，旧路径和新路径各3个独立进程，比较相同响应摘要及查询计划；输出组装阶段耗时和强制GC后的保留堆大小，不作为完整请求峰值、设备表现或生产容量结论。实际结果记录在生产化目标第十二批。

### 全局人手快照的内存控制

`RepairRepository.staffingContext()` 使用只读游标逐条解析工单，`StaffingContext` 仅保留调度、缺人汇总和接单卡片使用的字段，丢弃快照中的时间线、维修轮次、照片和联系方式；数据库中的完整记录保持原样，结算保存及跨住户提示更新仍重新读取完整工单。构造和保存后的快照刷新使用同一字段投影，原有缓存失效规则保持不变。

全部工单仍参与索引：已完成记录可能继续占用其时段，取消记录仍可能需要清除旧缺人提示，因此没有按“非活跃”一刀切过滤。接单卡片的描述、楼栋、旧房屋位置回查及 revision 仍保留。快照构建结束时游标已耗尽，结算写入不持有这个读游标；JSON解析失败和非对象仍跳过，游标读取故障向上传递。

可在 server 目录执行 `node --expose-gc --import tsx tool/repair-staffing-benchmark.ts` 重跑实验：6000条合成记录，其中80条待接单、12位师傅、每条20个历史事件及1600字描述；旧路径和精简路径各3个独立进程，验证调度、缺人提示、备选时段与接单列表摘要一致。强制GC后的快照保留堆中位数64,341,688→21,499,088字节，构建耗时328.53→323.63ms，查询计划均为SCAN repairs；这是内存优化，仍有全量扫描与JSON解析，不代表完整请求峰值、生产延迟或容量验收，完整记录见生产化目标第十三批。

### 师傅资料按编号一次分组

`readWorkforce()` 在当前调用内将技能和请假记录按workerId分组，再为每位启用的师傅取出对应数组；不再为每位师傅对全量关联表重复filter。仍执行原有四条SQL并保持读取顺序、人员顺序和各人的技能/请假顺序，skillsKnown继续由现存技能或技能审计共同决定，明确清空技能与从未登记的历史人员仍有区别，停用和非师傅账号仍不返回。

分组只在本次调用内存在，没有跨请求缓存；人员变更和事务回滚之后重新读取会取得最新值，各次返回的数组互不共享。新增复杂度回归中，40位师傅、720条关联记录的归属字段读取从27,320次降为720次；已有派单、休假、技能预览、接单池和停用回归通过。

在server目录运行 `node --import tsx tool/workforce-loading-benchmark.ts` 可复测：1000位师傅、3000条技能、1000条审计和6万条请假记录，旧/新实现各3个独立进程，每个进程预热1次后测量5次；每种实现15次读数的中位数5,170.73→49.50ms，返回内容摘要一致、四条查询计划相同。计时包含原有SQL读取和对象组装，不含人手匹配、结算、HTTP与GC暂停，不代表生产容量；全部关联表仍会读取，全量结算尚未解决，证据见生产化目标第十五批。

### 启动待办逐条重建与失败清理

`createApp()` 仍先结算全部工单，再重建通知；重建用只读游标逐条读取工单，不一次性保留全部原文。`Notifications.sync` 只写通知和投递表，因此同一连接上的通知事务提交/保存点回滚不会修改被遍历的工单；实际触发器故障测试已验证后续工单仍可处理，重启可补建失败待办，已读状态、原投递次数及重试时刻保持不变。

单条坏数据或通知生成失败继续隔离；初始结算、查询准备或游标读取的整体异常会关闭数据库并向上抛出，此时尚未创建推送定时器和HTTP入口。这只覆盖结算/重建块，不表示所有构造函数和后续初始化错误均已统一清理；重建前已提交的通知仍保留，重启沿用原有去重机制。

可执行 `node --expose-gc --import tsx tool/notification-startup-benchmark.ts`：真实createApp、隔离SQLite、6000条合成工单、每条20个事件与1600字描述、无推送设备，旧全量读取和游标路径各3个独立进程；生成6000条相同业务待办（比较时排除随机通知ID）。首次sync强制GC后的堆增量中位数60,432,112→10,920字节；重建阶段耗时5,848.35→6,308.75ms，约增加7.9%，是内存收益与时间开销的取舍。采样不是完整启动峰值或RSS，计时不含初始结算及采样GC暂停；仍扫描全表，单实例之外的锁竞争与生产负载尚未验收，证据见生产化目标第十四批。

### 客户端版本门禁（本地可配置基础）

`CLIENT_MIN_VERSION` 默认留空，保持原有客户端可访问；配置后重启服务，所有业务 API（包括发码、登录、刷新、公告和会触发结算的 GET）都要求 `X-Client-Version` 与 `X-Client-Platform`。版本使用正式的 `major.minor.patch`，按三个整数比较，每段最多6位且无前导零；不接受预发布或构建后缀。平台允许 ohos、web、android、ios、linux、macos、windows、fuchsia、admin-web，这只是标识校验，不代表这些平台已经构建或验收。缺失、非法或过低时返回 HTTP 426 / code 42600 和 `data.minimumVersion`，在业务处理前停止。

例：仅在核对当前配套客户端后将本地 `CLIENT_MIN_VERSION=1.0.0`；当前 pubspec 为 `1.0.0+1`，这里只比较 `1.0.0`。没有设定生产支持周期，也未默认开启门禁。健康检查、就绪检查、静态资源及原有带安装标识校验和限流的推送解绑不受此门禁限制；不能把所有 GET 都当成只读。维护进程仍优先返回503，并且不连接数据库。

`tool/flutter_ohos.ps1` 在 run/build/test 时从 pubspec（或显式 `--build-name`）注入 `HAVEN_CLIENT_VERSION`；不能用该 define 伪装成不同于构建的版本。绕过脚本构建时必须自行传入与产物一致的 define，未提供时发送空版本，在开启门禁的服务上会被拒绝；不从服务器最低版本生成客户端身份。物业网页在 `app.js` 中固定声明配套版本，回归测试核对其与 pubspec 一致；升级时同步修改并重新发布，私图请求也携带标识。

Flutter 在共用请求层携带版本和平台（包括刷新凭证），第三方请求不自动携带；426统一显示最低版本及“联系物业获取更新”，沿用现有 AppPrompt 和错误状态，不增加虚构的应用商店地址。拒绝不自动重试、不重放写入、不清除登录状态；刷新凭证期间收到426也保留当前账号，换号后的迟到响应仍丢弃。旧正式客户端是否能显示这条提示尚未验收。

版本头可由调用者伪造，因此只用于兼容提示，不能替代身份、角色、归属、revision 或回执校验；admin-web 不绕过版本门禁或管理员权限。版本不匹配会阻止请求触发的业务处理，但不会停止服务启动结算或后台推送。正式支持周期、分发地址、旧版本产物和完整跨版本业务验收仍待确定，G9仅部分完成。隔离真实联调脚本现在显式开启与当前产物匹配的门禁，并验证旧客户端写入被拒绝。

App 默认业务地址就是 `http://127.0.0.1:3000/`，不再有课程接口或后端切换开关。继续使用已有 `tool/dart_defines.local.env` 中的腾讯地图 Key，不修改或复制其中的秘密：

鸿蒙模拟器或手机上的 `127.0.0.1` 指设备自己，不能直接当成电脑。服务不监听局域网，使用 HDC 的设备到主机反向转发，让设备的 3000 对应电脑的 3000：

```powershell
# 在项目根目录 D:\haven_hub 执行
.\tool\forward_local_backend.ps1
.\tool\forward_local_backend.ps1 -DeviceId '设备ID' -List
```

Android 如需验收，执行 `.\tool\forward_local_backend.ps1 -Platform Android`，底层使用 ADB reverse。多台设备用 `-DeviceId` 指定，工具未自动找到时用 `-ToolPath` 指定完整路径；脚本用法及清理方式见根 README“鸿蒙或 Android 设备”。不要用代理、隧道或修改 `HOST` 重新暴露服务。脚本命令成功不代表设备已连通业务接口，仍需单独实测。

原生鸿蒙保持腾讯地图直连，不传 Web 的 `TENCENT_MAP_API_BASE_URL` 覆盖。登录凭证固定保存在 `flutter_enjoy_plus_local` 系列存储键，不读取课程接口时期的旧凭证；从旧版本升级或数据库换新后需要重新登录。

## 使用流程

1. 启动后端和 App，进入登录页，输入格式正确的虚构手机号，点击获取验证码。
2. 后端生成随机六位开发码，返回 `development: true`；App 自动填入，不发送短信。验证码五分钟有效，获取间隔60秒，五次输错后需重新获取。
3. 首次登录自动创建账号。账号开始时没有房屋；通过原有腾讯地图选小区，再选择楼栋、房间，上传两张示例图片完成添加。
4. 新增/编辑房屋统一进入“待审核”。物业后台可“通过”或填写原因后“打回”；住户修改同一份资料并重新提交。状态为“待审核、已通过、已打回”。
5. 提交报修返回最新完整列表；取消保留历史记录，状态变成“已取消”。创建访客也返回完整列表，并生成带 `LOCAL DEMO` 标识的 PNG 二维码，仅作展示和系统分享测试，不接真实门禁，也不实现自动核销/到期调度。

图片限8MB，服务端实际解码校验，限制1600万像素，转为最长边2048的PNG并去除元数据。所有 `/media/:id` 地址（包括历史地址）均要求 Bearer 登录凭证，未绑定图片仅上传人可读；证件按当前房屋审核对象授权，报修图按当前工单和当前指派师傅授权，改派后旧师傅的读取请求立即被拒绝。不存在和无权访问均返回404，响应禁止缓存。上传人可读取自己的图片；当前物业仍是整个实例的管理员，小区隔离尚未实现。

图片用途绑定会保留历史：删除房屋不会把旧证件图变成可公开或可用于报修、头像的图片；历史多用途图片按证件限制处理。Flutter 受保护图片通过 `requestDio.getMedia` 带凭证读取，内存展示并在换号、退出和销毁时清理；物业网页先鉴权下载再生成临时 blob 地址，不将 Token 写入 URL。第三方图片请求不带本服务凭证。旧客户端必须升级图片加载方式，直接打开媒体链接不再可用；这不是已完成的新旧客户端兼容方案。此学习服务仍请只使用示例图片和虚构资料。

## 接口与完整列表契约

成功响应仍是 `{ "code": 10000, "message": "成功", "data": ... }`，`GET /health` 例如返回 `{"code":10000,"message":"成功","data":{"mode":"local-learning","sms":false}}`。已知业务校验失败用非10000业务码；认证失效返回HTTP401，未知资源404，限流429。内部错误不把数据库或调用栈返回给用户。访问日志只保留时间、固定事件和请求ID、方法、状态、耗时，后台失败仅保留受限类别和HTTP状态，不记录手机号、验证码、Token、请求体或异常原文。

| GET `/management/workers/:id/account-events` | 物业查询最近50条账号状态事件，可用 `before` 序号向前分页 |

三个集合的写接口返回：

新版 `POST /repair`、`POST /visitor` 和创建房屋的 `POST /room` 可带 UUID 格式的 `submissionId`：同账号、同标识、同内容返回原 `createdId`，不同内容返回 HTTP 409 / 40902；已关闭标识返回 HTTP 409 / 40903。回执与创建同事务保存并跨进程保留，成功回执与关闭标识均不按时间自动删除；旧客户端不带标识时保持原接口行为。查询和关闭仅限当前账号作用域，其他账号查询已用标识与不存在的标识均返回 `unknown`，同一个标识可由不同账号独立使用。房屋编辑不得同时携带 `id` 与 `submissionId`。

房屋查询和关闭结果为 `{ "state": "unknown|created|closed|deleted", "createdId": "" }`；`created` 和 `deleted` 携带非空原房屋编号，其余状态为空编号。删除房屋保留原回执，查询或关闭返回 `deleted`，重放原创建返回 HTTP 409 / 40904，不会重新创建；重试已创建房屋返回当前完整列表，不覆盖后来编辑或审核的结果。新建房屋、回执、图片用途绑定和完整列表在同一事务中提交或回滚；仍检查账号归属、图片用途和英文姓名唯一性。

Flutter 房屋新建先取得已确认账号，每个账号持久保存至多一份待确认提交，保存失败不发送；页面重开后支持查询、确认后按原内容重试或安全停止，结果未知时保持待确认。确认创建或删除后清理对应回执并返回列表，清理失败保留回执并禁止重试。普通选房草稿仍可有多份且仅保存在内存中，使用随机 UUID 区分；恢复提交只清理编号和内容均匹配的原草稿，保护其他草稿及提交后修改过的草稿。编辑入口继续使用 revision，并不创建提交回执。

访客查询和关闭结果为 `{ "state": "unknown|created|closed", "createdId": "" }`；只有 `created` 携带非空邀请编号。`unknown` 不能证明创建失败，原请求可能仍在生成图片；关闭会在写事务内确认已有结果或保存永久关闭标识，返回 `closed` 后迟到的同回执请求也不能创建。生成图片前先查回执，写入前在事务内复查，邀请、图片及回执一并提交或回滚；房屋已删除也能找回此前成功的邀请。

Flutter 新版访客表单先取得已登录用户 ID，再按账号保存原始提交内容；落盘失败不发送，损坏数据不覆盖。重新进入页面可查询结果、确认后按原内容重试或停止；查到成功则清理对应回执并返回列表，查到停止后才允许编辑。清理失败保留回执并停用重试，换号或页面关闭后的迟到结果不导航、不删除别的回执。此流程不增加通用写请求自动重试。

```json
{
  "code": 10000,
  "message": "成功",
  "data": {
    "complete": true,
    "total": 1,
    "rows": [{ "id": "记录ID", "status": 1 }]
  }
}
```

示例只省略业务字段；真实行包含列表/详情所需字段。`rows` 是当前账号全部记录，按创建顺序倒序，编辑和取消不改变创建顺序。删除最后一条返回空数组和`total: 0`。

SQLite短事务中依次执行校验、写入、读取完整列表，再提交。如果构造列表失败，整个事务回滚。事务成功但响应在网络中丢失时，新版房屋、报修和访客按提交回执查询或显式重试；不带回执的旧创建请求仍不承诺断网重试绝不重复。

Flutter 的 `lib/utils/mutation_list.dart` 将这份响应暂存给下一次完整列表加载，消费一次后丢弃，后续手动刷新重新GET。普通分页响应不进入此通道；住户报修默认分页入口另读第一页，不消费完整列表缓存。列表不完整、解析失败、响应过期、会话变化或并发写顺序不明确时重新查询。解析列表失败不把已成功的写入改报成提交失败。房屋编辑返回详情时可直接从该列表读取对应记录。

### 确认修好的操作快照

报修列表、详情及返回完整工单的操作响应新增 `availableActions`，当前仅包含确认修好这一项；待接单池仍使用原来的字段白名单。示例：

```json
{
  "availableActions": [
    { "code": "confirm", "enabled": false, "reasonCode": "result_not_ready" }
  ]
}
```

| reasonCode | 含义 |
| --- | --- |
| 空字符串 | 当前可以确认，`enabled` 为 `true` |
| `resident_only` | 仅报修住户可确认，师傅和物业视图不可确认 |
| `not_in_progress` | 尚未进入可确认的维修阶段 |
| `result_not_ready` | 处理中但本轮尚未保存可确认的结果 |
| `revoke_pending` | 须先处理尚未结束的撤销申请 |
| `already_completed` | 已完成，不能重复确认 |
| `cancelled` | 已取消，不能确认 |

`policy.ts` 的只读判断同时供 `views.ts` 和 `actions.ts` 使用，沿用既有确认条件；查询和执行前仍由 repository 结算到期事项。快照不是授权凭证：`PUT /repair/:id/confirm` 仍只接收 `{ "revision": 数字 }`，在事务内重新检查归属、版本和当前状态，不接受客户端回传的操作字段；旧快照可能返回 409，客户端仅刷新，不自动重放确认。

Flutter 只在 `availableActions` 字段完全缺失时兼容旧响应的本地判断，且历史待确认工单也不能绕过未结束的撤销申请。字段已出现但为空、类型不正确、确认项缺失或重复、`enabled` 不是布尔真值、原因码未知或矛盾时不启用确认；未知操作码不生成按钮，原因文案由客户端本地映射，不直接显示服务端任意文本。确认弹窗期间换号或版本变化会终止提交，快速重复点击只打开一个弹窗，提交期间不并发刷新详情以免旧响应覆盖新状态。

本次仅迁移确认操作，其余操作仍沿用现有客户端判断；新增响应字段不代表已建立正式的客户端支持版本策略，见生产化目标 G9。

## 数据和代码入口

- `src/app.ts`：HTTP路由、请求校验、上传、响应与错误出口。
- `src/auth.ts`：开发码/腾讯短信验证码、账号、随机访问凭证与刷新凭证（不是 JWT）；数据库仅存验证码和Token哈希，模式隔离；`src/sms.ts`负责TC3签名及短信发送。
- `src/community/service.ts`：房屋/访客规则，账号权限，写入后返回完整列表；报修规则位于 `src/repair/`。
- `src/database.ts`：SQLite建表迁移、参数化SQL、事务。`users/sessions/codes/uploads` 保存基础数据；`rooms/repairs/visitors` 各自保存ID、账号、顺序以及校验过的JSON业务字段。
- `src/config.ts`：集中读取并校验环境变量。

当前按单实例单小区方案推进：同步数据库连接串行处理短事务，短信网络请求在事务外等待；没有连接池、分布式缓存或音频转写引擎。腾讯短信已实现适配但未验收真实收信。物业后台位于 `/admin/`，维修人员使用 App 内独立工作台；完整列表仍会随记录量增长，容量承诺需依据正式负载验收。

## 房屋审核与报修派单

报修的五个可视节点为：住户申请 → 物业派单 → 待接单 → 处理中 → 已完成。物业派单后由被指派的师傅接单，接单直接进入处理中，师傅本人提交完成。

返修次数不设上限，每轮售后期均从住户确认或系统最终自动确认完成起算 720 小时。开启返修时 rounds 只保留当前轮内容，历史已完工费用单独保存在 fees；派单改人或师傅退出会清空当前未完工轮的处理结果、费用和可确认标记，不改历史费用。从未登记技能的原师傅可继续持有旧单；明确清空或技能不匹配、师傅已不存在时交物业协调。

首次配置物业账号（在 `server` 目录运行；使用你选定的开发手机号）：

```powershell
npm run role -- 19900000002 admin
npm run build
npm start
```

浏览器访问 `http://127.0.0.1:3000/admin/`，使用该手机号和开发验证码登录。后台“维修人员”可添加师傅的姓名和独立登录手机号。师傅在连接同一服务的 App 登录后自动进入维修工作台。角色由后端校验，普通登录和个人资料接口不能自行提升权限。

独立演示环境使用 `npm run demo`，端口3010，数据库 `data/workflow-demo.sqlite`，不会修改 `data/haven.sqlite`。内置虚构账号：住户19900000001、物业19900000002、师傅19900000003。首次启动创建示例房屋和报修，后续启动保留操作结果。

维修工作台网页先在项目根目录构建一次：`.\tool\build_workflow_web.ps1`。随后在 `server` 目录运行 `npm run demo`，同一个服务提供物业后台 `http://127.0.0.1:3010/admin/` 和师傅入口 `http://127.0.0.1:3010/workflow/#/worker`。师傅使用 `19900000003` 获取开发验证码并登录，验证码会自动填入。终端需要保持运行；不要双击 HTML 文件或使用 `file://` 地址。修改 Flutter 页面后重新构建再刷新。

数据库启动时按版本事务迁移，当前版本为13；版本8增加报修提交回执，版本9增加图片用途绑定、账号停用状态和账号变更历史，并回填历史图片关联；版本10增加按账号与提交标识唯一的 `visitor_submissions`，保存成功邀请编号或关闭标识；版本11增加 `room_submissions`，按账号与提交标识唯一，保存原房屋编号或关闭标识，房屋删除后仍保留原编号；版本12增加追加式 `management_audit`，版本13增加验证码/会话模式、持久短信预算及数据库环境标识。房屋编辑、审核及报修操作携带 `revision`，旧页面重复操作或并发覆盖返回409，刷新后再处理。新建报修最多8张本人已上传且用途兼容的照片。容量设置的默认值、星期模板和单日覆盖共用一个内容版本：GET `/management/repair-capacities` 返回 `revision`，所有 PUT/DELETE 都必须回传该版本；两个物业页面同时保存时，旧版本返回409且不写入，页面保留未保存输入，人工刷新后再核对。版本只用于并发保护，不是权限凭证。生产升级前须备份并验证隔离恢复；旧程序会拒绝版本13，不能仅换回旧程序并继续使用迁移后的数据库。本批仅在隔离测试数据库验证迁移，未执行生产升级或改动日常开发数据库。

管理审计入口为 `/admin/audit.html`，沿用物业工作台会话；GET `/management/audit-events` 仅启用物业账号可读，支持 `actorId`、`targetType`、`targetId`、`action`，`limit` 默认50且最多100，`before` 传上页 `nextCursor`，按追加序号倒序读取。`targetType` 为room、repair、worker、capacity-default、capacity-weekday或capacity-date，`action` 枚举见 `src/management-audit.ts`。返回rows及nextCursor，前后快照仅包含必要决策字段，不复制姓名、手机号、证件、图片、凭证和自由文本；更早分页固定沿用上次提交的条件。

18种业务管理变更与审计在原有事务内同时提交或回滚；操作前已完成的到期结算仍独立保留。改约确认的409可能伴随已提交的提议失效，此时记录实际变化。迁移只导入已存在的账号事件和最后一次技能变更，来源分别为legacy-account和legacy-skill-latest，未知历史不补造；新事件来源live。审计表禁止普通更新和删除并随数据库备份恢复，但无法防止数据库所有者改写，保留与归档政策待定；物业角色CLI、审计读取日志及运维安全审计另行建设。

房屋更新契约：`POST /room` 创建时不要求版本且服务端从1开始；带 `id` 的编辑必须回传详情中的非负整数 `revision`，缺少或过期返回 HTTP409/code40900，非法类型返回 code40000，均不写入。历史记录没有版本字段时读取为0，编辑须显式提交0。归属与版本检查、保存及完整列表返回共用已有写事务，版本不能代替账号授权。住户编辑和物业审核每次成功都递增版本，因此旧住户表单不能覆盖刚完成的审核，旧物业页面也不能审核新提交的资料；这项版本保护本身未增加数据库迁移。Flutter 编辑与冲突恢复强制读取最新详情，冲突保留输入并停用提交，用户确认替换后才重新加载；读取失败继续保留输入，成功后展示最新审核状态且不自动提交。不携带版本的旧客户端将无法编辑或删除房屋，需配套更新客户端；当前已注册DELETE入口的版本与事务契约已核对，无回执旧客户端的创建去重、生产回执保留政策及正式客户端版本支持策略仍未完成。

房屋删除契约：`DELETE /room/:id` 的 JSON 请求体为 `{ "revision": 7 }`，使用用户确认删除时查看的非负安全整数版本；历史无版本记录须显式提交0。服务端在同一事务内先检查当前账号归属，再校验版本、删除并返回完整列表；缺少或过期版本返回 HTTP409/code40900，非法版本或额外请求字段返回 code40000，均不删除。房屋已删除或无权访问返回404；并发删除只有一方成功，另一方404，响应丢失后的404不能区分是谁删除。列表构造失败会回滚删除，成功删除仍保留创建回执，迟到创建不会复活原房屋。

Flutter 删除弹窗使用已显示的房屋与版本，弹窗、请求、刷新和编辑互斥；取消不发请求，成功沿用完整列表回执。冲突或其他删除错误后停用修改与删除，用户须显式刷新当前资料，再次确认才能重新发起，刷新失败保留旧内容但不恢复操作；刷新返回404时移除旧详情与操作按钮，不把它当成此次删除成功。换号立即隐藏旧账号详情，迟到读取、删除响应和页面销毁后的结果均不更新或导航。既有编辑返回后仍刷新详情并使用更新后的版本；没有通用自动写重试，也未增加数据库迁移。

报修撤销契约：`PUT /cancel/repair/:id` 与 `PUT /repair/:id/revoke` 均要求查看时的非负安全整数 `revision`；缺少或过期版本在归属检查后返回HTTP409/code40900，非法版本或额外字段返回code40000，历史无版本记录须显式提交0。直接取消仅接受待处理或已分配但未接单工单，成功返回完整列表；已接单后即使提交 `notified: true` 也不能通过直接取消入口创建撤销申请，须使用 `/repair/:id/revoke`，该入口返回更新后的单个工单。原有到期结算独立提交；撤销、版本递增及完整列表在既有写事务内完成，列表失败会回滚撤销。版本不是权限凭证，越权仍返回404。

Flutter 撤销确认使用已查看的编号和版本，弹窗期间换号、刷新中的状态或新版本会终止旧确认；请求期间禁止并发刷新和其他操作。直接取消与撤销申请失败后停用操作，须主动刷新成功再重新确认，失败刷新和自动回到前台不能解除限制；刷新已取消状态或404只展示最新结果，不声称本次请求成功，也不自动重放写请求。换号立即隐藏旧详情，迟到响应和页面销毁后的结果不更新页面、不提示成功、不导航。不发送版本的旧客户端取消与撤销申请会被拒绝，必须配套更新，正式客户端支持策略仍未完成；本批无数据库迁移。

师傅停用前须先按已有改派规则交接或完成在手工单及待处理事项；接口不自动替物业选择接手人。停用清除会话、验证码和推送设备登记，取消尚未完成的投递并关闭待办；已发送到外部推送服务的消息无法撤回。停用期间不能发验证码、登录、刷新或访问工单、图片，恢复后必须重新登录。变更原因、操作者、时间和状态按事件追加，网页展示最近50条；这仅覆盖师傅账号状态历史，不等于全部管理操作审计已完成。

## 容量配置的并发写入契约

GET `/management/repair-capacities?date=2026-10-29` 返回原有字段，以及 `templates`（七天模板）和 `revision`（64位十六进制内容版本）；省略日期则返回默认容量视图。页面从这一份事务快照展示三层配置，不再拼接两个不同时间的 GET。GET `/management/repair-capacities/weekdays` 仍返回原来的星期映射，写入前应从主查询取得完整快照。

所有容量 PUT 请求为 `{ "revision": "<读取结果中的版本>", "capacities": { "10": 8 } }`；清空星期或日期覆盖的 DELETE 请求为 `{ "revision": "<读取结果中的版本>" }`。缺失或格式错误沿用参数校验的业务码40000，旧内容版本返回HTTP409/40900，均不改动配置；新版网页提供刷新提示，旧版网页必须重新加载后才能继续写入。PUT仍为部分更新，空白输入不会删除已设值；清空必须使用对应DELETE。

版本比较和全部时段写入处于同一个 `BEGIN IMMEDIATE` 事务，写入失败全部回滚。默认、星期、单日所有容量配置共用内容版本，因此修改另一日期也会使旧页面失效；先采用这一明确规则，不自动合并冲突。版本只取决于配置内容：相同内容、数据库重开或恢复为相同配置时版本相同，它不是递增计数或操作审计；预约数量和师傅人数变化不会更改容量版本。每次请求仍须物业角色授权。

冲突页保留当前输入并禁止再次提交，用户点击“重新加载容量”会换成最新配置，需要重新核对和填写；系统不会自动用新版本重放旧输入。成功写入后刷新配置，返回内容仍遵循原有默认/星期/日期接口形状；需要下一次写入时重新读取主快照。容量版本保护本身不需要数据库迁移。

## 错误回执

服务端响应携带 `X-Request-Id`，跨域允许读取该响应头；Flutter 网络和业务异常携带有效的 UUID v4，已接入的报修、访客、师傅、个人资料与通知错误提示以及物业网页提供“复制排查编号”。复制内容只有编号，服务端可按编号关联脱敏日志。未取得服务端响应的断网错误不会伪造服务端回执；远程日志保存和告警尚未接入，也未把全部字符串错误入口改完。

## 运行指标与本地检查

GET `/management/operations` 仅启用的物业管理员可读，沿用会话及最低版本门禁，每来源IP每分钟最多12次；提供单进程约10分钟的请求/错误/固定耗时分桶和后台异常计数，以及有效待办的推送积压、退避、耗尽重试和领取超时汇总，不返回账号、通知内容或设备凭证。

`npm run operations:check -- C:/private/haven-operations-check.json` 使用仓库外配置及凭证文件，依次检查健康、就绪和指标，仅连接数字回环地址；退出码0表示当前阈值通过，1为不可用，2为超限，3为维护或样本不足。配置参考 `operations-check.example.json`，示例阈值不是生产标准。

推荐独立只读模式 `authentication: "operations-key"`：`npm run operations:key -- <全新绝对目录> <未来UTC到期时间>` 生成受限的原文文件和摘要文件，终端不输出密钥；设置服务端 `OPERATIONS_KEYS_FILE` 指向摘要文件后才启用 GET `/operations/snapshot`。该凭证只能读运行汇总，不能访问业务、图片或刷新接口；支持最多两把有效期重叠的钥匙轮换，每次请求重新读文件，删摘要立即拒绝后续请求，坏文件不保留旧授权。原 `admin-session` 模式仍支持但受管理员会话到期限制。未配置实际运行密钥、定时任务或外部告警，字段、生成/轮换步骤和验收边界见 [运行指标与故障检查](../docs/operations_monitoring.md)。

持续采集可执行 `npm run operations:monitor -- C:/private/haven-operations-monitor.json`，配置参考 `operations-monitor.example.json`；它以独立进程串行运行检查，至少间隔30秒，达到连续失败/恢复次数后在专用SQLite中记录故障变化，并输出脱敏JSON。重复故障不重复建立故障编号，重启保留未恢复故障编号，保留条数必须显式设置；只支持独立监控钥匙，既有一次性检查命令保留。进程锁、日志写入失败处理及运行方法见上方手册，未安装系统服务、开机任务或外部告警；`--cycles 3` 可做有限次数演练，其退出码0只表示采集正常结束。

采集器自身状态可用 `npm run operations:monitor:status -- C:/private/haven-operations-monitor.json` 独立检查：只读取提交后原子发布的状态文件及锁，不打开SQLite、读取钥匙或发送HTTP。区分采样新鲜、首次采样等待、正常停止、过期和不可用，外层新鲜不代表业务健康；正常停止和采样过期返回2。第二十六批升级需使用全新日志目录，保留旧历史；期限、时钟异常及退出码见[运行手册](../docs/operations_monitoring.md)。系统调度和外部告警仍未配置。

Windows可用 `tool/run_operations_job.ps1` 调用Monitor/Status模式，自动核对固定Node版本和构建产物并保留检查退出码；`tool/export_operations_tasks.ps1` 可生成当前账号登录后的采集/每分钟状态检查XML，拒绝覆盖旧文件，仅生成并本机解析，不注册任务。账号、目录、导入和实际调度验收范围见[运行手册](../docs/operations_monitoring.md)；这不是无人登录时启动的生产服务，旧进程锁仍须人工核实后处理。

## 可选运行日志保存

第二十八批支持 `RUNTIME_LOG_DIRECTORY`，填新的专用绝对目录即可启用脱敏JSONL文件；父目录须存在，不能与数据库、监控或备份共用。默认留空，不改日常配置；不需要短信密钥。`RUNTIME_LOG_MAX_BYTES` 默认1048576、`RUNTIME_LOG_MAX_FILES` 默认5，按大小分段并淘汰最旧文件，数量包含当前分段；每次重启新开一段，按数量保留不等于生产保存期限。

文件记录可按页面排查编号查找，标准输出也使用固定字段白名单；写盘失败仅输出一次脱敏故障标识，后续 `/ready` 返回503，`/health` 仍表示进程存活。关闭/轮转会刷新文件，日志失败时正式入口关闭返回1；已有活动或遗留锁不会被自动删除。维护模式继续不打开日志目录，远程收集和外部告警仍未接入，详细启用、查询、保留、故障和锁恢复说明见[运行手册](../docs/operations_monitoring.md)。

## 启动失败与服务关闭

第二十九批为正式 `main.ts` 入口补齐统一收尾：收到SIGINT/SIGTERM处理事件后停止接收新连接和周期任务，同时等待现有HTTP响应及在途推送结束，随后关闭资源；重复关闭共用同一次流程。默认5秒等待到期则记录固定故障并返回1，不在任务仍使用数据库时提前关库。正常完成返回0，配置、启动、监听、后台停止、资源关闭、日志失败及致命异常均返回1。

启动错误和JavaScript未捕获异常仅输出固定事件，不回显异常原文或配置值；进程异常记录后会进入退出，不继续长期服务。启用文件日志时保存关闭前仍可写的阶段事件，最终 `server_stopped` / `server_shutdown_failed` 记录在标准错误。维护模式仍不打开数据库和日志目录，系统强杀/原生崩溃不保证执行收尾；Windows真实控制台/系统任务停止仍待部署验收，详见[运行手册](../docs/operations_monitoring.md)。

## 备份与维护

在 `server` 目录执行，源数据库必须存在，目标父目录须存在，目标备份或恢复目录必须是全新目录：

```powershell
npm run backup -- create data/haven.sqlite D:/haven-backups/release-20261028
npm run backup -- verify D:/haven-backups/release-20261028
npm run backup -- restore D:/haven-backups/release-20261028 D:/haven-restores/candidate-20261028
```

备份使用 SQLite 在线备份接口，包含已提交的 WAL 内容及 `uploads` 图片；清单保存文件 SHA256、数据库版本、各表行数和内容摘要，并检查完整性和外键。Windows 目录限制为执行账号与 SYSTEM，POSIX 目录为0700；没有实现异地加密存储、定时计划或保留策略。校验用于检测损坏，不是防止有目录写权限者同时篡改清单和数据的数字签名。恢复只写入新目录，绝不覆盖运行中的数据库。

`MAINTENANCE_MODE=true` 启动独立维护进程，完全不打开数据库、不迁移、不触发读请求结算或后台推送；`/health` 返回200且标明维护模式，`/ready` 和全部业务读写返回503，带 `Retry-After: 60` 和排查编号。必须先停止原正常进程及其他写入工具；修改环境变量不能停止已运行进程。维护进程继续遵守本地监听限制。完整步骤和恢复写入后的数据损失边界见 [备份恢复演练手册](../docs/backup_restore_runbook.md)。
